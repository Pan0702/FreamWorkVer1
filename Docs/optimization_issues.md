# GPUインスタンシング計測で見えた課題

`CpuProfiler` で木の個別描画（`Tree` を Actor として大量生成）と GPUインスタンシング（`InstanceTrees`）を比較した際に見つかった課題をまとめる。

## 計測結果（参考）

Release x64、Tree の MeshCollider を外し、`kCBAllocatorSize` を 100MB に拡張した状態での CPU 時間（ms / frame）。

| 区間 | 4万本 個別 | 4万本 Instancing | 16万本 個別 | 16万本 Instancing |
|---|---|---|---|---|
| Game Tick | 0.557 | 0.033 | 2.023 | 0.082 |
| Collect Total | 2.917 | 0.336 | 13.341 | 1.556 |
| Shadow Pass | 1.130 | 0.253 | 4.759 | 1.068 |
| Main Pass | 7.440 | 0.209 | 22.427 | 0.920 |
| Render Total | 8.616 | 0.587 | 27.272 | 2.810 |
| ドローコール | 40,001 | 2 | 160,001 | 2 |

GPU 時間は未計測。

---

## 優先度：高

### 1. 定数バッファアロケータの容量不足で描画が黙って消える
- 場所：`Src/Engine/render_system.cpp`（`kCBAllocatorSize`）、`Src/Graphics/constant_buffer_allocator.cpp`
- フレームごとの `ConstantBufferAllocator` は 1MB 固定。確保は 256 バイト単位のため、1フレームで使えるのは 4096 枠しかない。
- `Allocate` が失敗すると、各 `Submit` はログも出さずに `return` / `continue` する。
  - 個別描画では、3,600本の時点でシャドウパスが 3,601 枠を使い、メインパスは約 240本しか描けていなかった。
  - 10,000本では、シャドウパスが全枠を使い切り、メインパスで何も描かれなくなった。
  - インスタンシングでも、10,000本（行列 625KB × 2パス）で木が消えた。
- 計測用に 100MB へ拡張したが、3フレームぶんで 300MB の Upload ヒープを常に確保することになり、恒久対応にはならない。
- 対応案
  - `Allocate` の失敗を検出してログを出す（1フレーム1回で十分）。`CpuProfiler` のカウンタにも失敗回数を出す。
  - 容量を固定値にせず、不足したときに拡張するか、ページ単位で追加確保する。
  - インスタンスデータを CB アロケータから切り離す（課題 2）。

### 2. インスタンス行列を毎フレーム2回アップロードしている
- 場所：`Src/Renderer/instanced_mesh_renderer.cpp`（`Submit` / `SubmitDepth`）
- シャドウパスとメインパスで、同じインスタンス行列をそれぞれ `Transpose` し、それぞれ CB アロケータに書き込んでいる。
- 定数バッファ用のアロケータに大きな StructuredBuffer を載せているため、課題 1 の容量不足を招きやすい。
- 対応案
  - Collect の時点で転置済みの配列を作り、1フレーム1回だけアップロードして、両パスで同じ GPU アドレスを使う。
  - インスタンスデータ専用の Upload バッファ（リングバッファ）を用意する。

### 3. 静的インスタンスを毎フレーム作り直している
- 場所：`InstancedMeshRenderer::Collect`
- 木は動かないのに、毎フレーム全インスタンスの `local * owner_world` を計算し、`gpu_instances` に詰め直している。
- その結果、インスタンシング後も CPU 時間はインスタンス数にほぼ比例して増える（4万 → 16万本で Render Total が 0.587 → 2.810ms、Collect が 0.336 → 1.556ms）。
- 対応案
  - インスタンスの追加・削除・移動・Actor の移動があったときだけ更新する（dirty フラグ）。
  - 静的インスタンスは Default ヒープに一度だけ転送し、常駐させる（`CopyBufferRegion` + `COPY_DEST` → `NON_PIXEL_SHADER_RESOURCE` のバリア）。
  - 更新時は GPU が読み終わるのをフェンスで待つか、フレーム数ぶんのバッファを持つ。

### 4. 当たり判定が総当たりで、メッシュコライダーが非常に重い
- 場所：`Src/Engine/collision_world.cpp`（`Collect`、`ContactMesh*`、`Raycast`）
- `CollisionWorld::Collect` は全ペアの総当たり（O(n²)）。コライダー 3,600個で約650万ペアになる。
- ブロードフェーズがないため、プレイヤーとメッシュコライダーの判定で毎回全三角形を `TransformPoint` している。
- `Character` の接地判定 `Raycast` も、全メッシュコライダーの全三角形を毎フレーム走査している。
- 木 3,600本に MeshCollider を付けた状態で、Release の Game Tick が 78.8ms になった。
- 対応案
  - 判定前に AABB 同士の判定で弾く（ブロードフェーズ）。空間分割（グリッド / BVH）も検討する。
  - 静的コライダー同士のペアは判定しない。
  - メッシュの三角形はワールド座標に変換済みのものをキャッシュする（静的な場合）。
  - 木のような装飾物はカプセルや Box などの単純な形状にする。

## 優先度：中

### 5. 視錐台カリングがない
- 個別描画・インスタンシングとも、画面外のオブジェクトも全部描いている。
- シャドウパスも、ライトの正射影範囲の外にあるものを含めて全部送っている。
- 対応案：インスタンス単位で AABB と視錐台の判定を行い、見えるものだけを詰める。

### 6. 個別描画でドローごとに同じステートを設定し直している
- 場所：`MeshRenderer::Submit`
- サブメッシュごとに、ルートシグネチャ、PSO、ディスクリプタヒープ、ライト CB、シャドウ、Irradiance を毎回セットしている。
- 16万本で Main Pass が 22.4ms になる主な原因。シャドウパス（1本あたり CB 1つと Draw だけ）は 4.8ms で済んでいる。
- 対応案：描画アイテムを PSO / マテリアル順に並べ、前回と同じステートの設定を省く。

### 7. 静的な装飾物を Actor として大量に持つコスト
- 16万本を Actor として生成すると、コライダーなしでも Game Tick が 2.0ms、Collect Mesh が 10.9ms かかる。
- 対応案：静的な装飾物は Actor を作らず、インスタンス配列として持つ。`InstanceTrees` の方式を標準にする。

## 計測まわり

### 8. GPU 時間を Release で取れない
- `PerformanceProfiler`（GPU タイムスタンプ）は `_DEBUG` のときだけ有効。CPU は Release で測るのに、GPU は Debug でしか測れない。
- 対応案：GPU タイムスタンプ計測も Release で使えるようにし、`CpuProfiler` と同じ bool で On/Off する。

### 9. カウンタが「実際に描画できた数」ではない
- `Mesh Commands` などは Collect 時点の件数。課題 1 のように Submit で失敗しても数字は変わらないため、描画が欠けていることに気づけなかった。
- 対応案：Submit 側で実際に発行したドローコール数をカウントする。

### 10. 計測用の一時的な変更が作業ツリーに残っている
- `kRange = 200`、`kUseInstancedTrees = false`、`kCBAllocatorSize` 100MB、Tree の MeshCollider 削除、起動レベルを Test2 に変更。
- コミット前に元に戻すか、計測用の設定として切り替えられる形にする。
